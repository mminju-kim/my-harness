# 허들링 앱 — 작업 방식 (AI 없이 손으로 했던 마지막 경험)

> `story-service.md`는 "무엇을 위한 일인지", 이 문서는 "내가 실제로 어떻게 했는지"를 정리한다. 둘을 섞지 않는다.

## 단계

| # | 한 일 | 명사 (산출물) | 경계 (넘어가는 곳) |
|---|---|---|---|
| 1 | 나는 기획(정책, 서비스 화면 설계 문서)을 검토한다. | 입력: 정책 문서, 화면설계서 (현재는 `docs/prd.md`로 대체) | 👥 기획자, PM, 또는 클라이언트에게서 받음 |
| 2 | 나는 uibowl에서 경쟁사의 UX 부분과 UI 기능 디자인 레퍼런스를 모으고 분석한다. | UX 레퍼런스, UI 기능 디자인 레퍼런스 | 🛠 uibowl |
| 3 | 나는 Figma에 레퍼런스와 화면설계서를 반영한 키스크린 2~3개를 390×844로 그린다. | 키스크린 시안 2~3개 | 🛠 Figma |
| 4 | 나는 내부 관계자와 협의해 컨셉 시안을 확정한다. | 확정된 컨셉 시안 | 👥 내부 관계자 |
| 5 | 나는 확정된 시안으로 디자인 토큰과 컴포넌트를 만들고 화면 디자인을 한다. | 디자인 토큰, 컴포넌트, 화면 디자인 | 🛠 Figma |
| 6 | 나는 완성된 시안의 토큰과 컴포넌트가 가이드를 어겼는지 검토한다. | 가이드 위반 검토 결과 | 기준 문서: `docs/design.md` |

## 게이트

게이트는 단계 사이에만 둔다. 6단계 뒤에는 게이트가 없다. G1과 G3는 합치지 않고 따로 둔다.

| 게이트 | 위치 | 컨펌하는 사람 |
|---|---|---|
| **G1. 레퍼런스 분석 컨펌** | 2 → 3 | 나 |
| **G2. 컨셉 시안 컨펌** | 4 → 5 | 나 (내부 관계자와 협의한 뒤) |
| **G3. 화면 디자인 컨펌** | 5 → 6 | 나 |

## 흐름

```txt
1 기획 검토 → 2 레퍼런스 분석 → [G1 나] → 3 키스크린 → 4 협의 → [G2 나] → 5 토큰·컴포넌트·화면 → [G3 나] → 6 가이드 검토
```

## 기준 문서

- 1단계 입력: 별도 정책 문서·화면설계서가 없어 `docs/prd.md`를 기획 문서로 쓴다.
- 6단계 검토 기준("우리 가이드"): `docs/design.md`.
